# CLAUDE.md - Balamb Garden

Dalamud plugin for FFXIV gardening: census, timers, and one-press tend/harvest/replant chains for the household's estates. Command: `/garden`. This doc is the machine - how the code works, as it stands. It states what IS; the history of how it got here lives in the maintainer's private notes, and owed work lives in tickets, never in this file. Product direction and design rationale live in the maintainer's private notes (the Rebuild Spec is canonical). Reviewed at every merge to main.

## Build laws (read first)

- **Always `-p:Platform=x64`.** An unflagged build produces a stale/mismatched DLL that Dalamud loads anyway.
- **Agents NEVER build the plugin.** Dalamud hot-loads the output DLL - any build is a live deploy into a running game. Builds happen only on the player's explicit "go", never while they may be in-game or testing. Dalamud does not auto-reload a rebuilt dev plugin; the player reloads it from the plugin installer.
- **Tests are safe anytime**: `dotnet test BalambGarden.Engine.Tests/BalambGarden.Engine.Tests.csproj` - the Engine has zero game dependency. A compile check of the plugin project goes to a scratch output folder (`-o <scratch>`), never to the dev-load path.
- Feature branches only; merge to main (no-ff) = save point; this doc's review rides every merge.
- Repo is quasi-public. The maintainer persona is **Drift** (GitHub: DriftlessDigits); no real names in code, comments, commits, or docs; no private paths, workspace or tooling names. No AI co-authorship lines in commits. A machine-local pre-commit name guard backs this up (installed per machine from the maintainer's own tooling; untracked BY DESIGN - a tracked hook would ship the names it blocks).

## Architecture: five layers, one-way flow

Each layer knows only the layer below. **Acting IS censusing**: chains emit dialogue receipts that flow back in through the pump.

1. **Sensing** (`Engine/Sensing/` + `BalambGarden/Game/`) - stateless readers.
   - `MapSensor`: housing DataMap decode - outdoor 48-byte entries (8 beds per patch key), indoor per-pot sub-entry 0. Formats in `Engine/Sensing/MapFormat.cs` (bytes 4-5 are allocator junk - never read them). **Indoor zeroed entries are KEPT as unoccupied readings**: a harvest zeroes an entry in place, so a zeroed entry is the map positively saying "empty"; an all-empty room is proof the map answered. Consumers wanting growing pots filter on `Occupied` themselves (Water All and the replant settle poll do).
   - `ObjectSensor` / `GimmickId`: nearby bed objects - GimmickId bytes carry [bed index][patch ordinal][patch-id u16]; reach verdicts at full precision.
   - Pot identity is a **direct read** off the pot object: `HousingFurnitureIndex` + `BaseId` (= HousingFurniture sheet row). `FlowerpotSheet` derives the 3 flowerpot rows by name scan, fails loud on drift.
   - `RosterSensor` / `EstateSensor`: permission from real game data - HouseId direct equality decides "ours"; unfittable rows fail CLOSED and log raw.
   - `PotPigment`: indoor byte 2 = (pigment<<4)|stage; only receipted nibbles are interpreted, a color is never guessed.
2. **Census** (`Engine/Census/`) - the join and record brain. A row is CREATED by a sighting on a listed (rostered) estate; a bed is BOUND to a map key only by a receipt: `JoinShortlist` proposes patch<->key candidates from diffs, `JoinConfirm` keeps exactly one survivor or nothing. **There is no Claim() method and no pattern-bind path.** Receipted interactions are `ReceiptEvent`: Tend / Harvest / Plant / PotWater. `AccessRoster` scopes the census: not listed = not tracked.
3. **Ledger** (`Engine/Ledger/`) - `LedgerStore` persists the beds + bindings (file `Version` 4). `ClaimedBed` = **one bounded planting record per bed** - a planting is one plant's life in one bed, sow to harvest: `Latest` (newest content read), `PlantedAt`/`PlantedBy`/`PlantedSpecies`, `StageSeen[stage] = first/last seen` (one bracket per stage, min/max fold, replay-idempotent, never evicted), `LastTended`/`LastTendedBy`/`LastTendedSpecies`, and the fence `PlantingResetAt`/`PlantingResetReason`. **THE RULE**: an older receipt never overwrites newer evidence - if it agrees with the current plant it adds its evidence (`Absorb` -> FoldedOlder), if it contradicts it goes to history only (ledger untouched, counted as replant evidence); only evidence NEWER than everything it contradicts may reset a bed. The fence only moves forward and writes at or before it are no-ops. The fence and the older-test apply to receipts from the other install; this install's own live acts and own live map reads are never measured against it (they are, by definition, the newest thing this install knows). `Rebase(reason, cut)` is the one reconcile path and is **reasoned, logged, time-aware**: every reset names a `RebaseReason` (HarvestWitnessed / ReadsEmpty / NewPlantingSighted / PotAbsent / PlantReceipt), removes only evidence at or before its cut (a sighted replant cuts at the old planting's newest content evidence; a plant receipt cuts at the sowing instant), and returns a `RebaseEvent` the plugin logs (`CensusPump.ReportRebases`: INF when anything was removed or a harvest was witnessed, DBG otherwise) and appends to the trail. **The game wins on content mismatch**, and **a Harvest receipt rebases the record at once** (the receipt is the emptying witness - the row stays, contents and clocks leave); the two-settled-reads reconcile is for UNWITNESSED harvests only. `Hand` = own vs an opaque wire slug - the ledger never holds a name. `DebugTrail` (trail.jsonl) is append-only evidence the engine never reads back. `GardenHistory` (`history.json`) = every Plant and Harvest from every hand, forever, with yields and (harvests) the cross seed in three states; `HistoryQuery` is the read side (no screen reads it yet - that is phase 2, a ticket).
4. **Derivations** (`Engine/Derivations/`) - pure functions. Every timer is an `EtaWindow` (never a point) with `Provenance` (anchored / bracketed / estimated). `StageModel.RipeWindow` anchors on `PlantedAt` when present, otherwise brackets from the `StageSeen` first/last instants (two or more stages seen = bracketed, one = estimated). The fence is a floor on the sowing (every reset cuts at or before the old contents were last true): when `PlantingResetAt` tightens the earliest end, the window is bracketed - "emptied at X, seen growing at Y" pins a fresh replant to minutes; a fence that would invert the stage bracket is ignored, never a contradiction. `ClockWiltSource`: Watered -> Due -> Overdue -> Danger from last-tend + crop wilt hours; `DiesAt` = tend + witherHours; live stage 4 (ripe) forces NotApplicable - fully grown cannot wilt. `PotWiltRule`: a pot's map wilt byte claims water only at `wilt==1 && stage<4` (ripe pots broadcast nonzero b4 while the game offers no watering verb at stage 4 - both dashboard call sites consume this one rule). `TendSweep`: whether a bed belongs in a tend SWEEP - skip only what the live map CONFIRMED ripe/empty, FAIL OPEN on map silence; single-bed presses are never filtered. `PipelineReader` = tips: advisory sentences over recorded plantings + CrossbreedPairs, never a planner. `PotCyclePlanner` builds full plans or refuses (never a half-plan); soil rule: exactly one soil in bags = the soil, else picker. `RunPace`: EWMA (half-old/half-new per completed unit) behind the run-log ETA; pace is TRACKED, never predicted (a pot sweep only learns its verb when the menu opens). Per-chain seeds match dialogue shape; `ChainBase.Eta` is thin wiring over it.
5. **Verbs & UI** (`BalambGarden/Chains/` + `Windows/`) - `ChainBase`: paced dialogue chains (human tempo + jitter, occupied-player guard, clean stop with stated reason; stops land during human-wait steps). `TendChain` (`TendOne` for deliberate single presses; `TendMany` for sweeps - the caller filters through `TendSweep` at the button, where the count is claimed, and the chain does not re-filter), `CycleChain` (harvest + replant beds), `PotChain` (pot cycle incl. full-auto plant, `WaterMany` = the pot Tend All - the button counts only occupied non-ripe pots off the live map), with `PlantFlow`/`PlantFill` doing the read-and-click (no pacing, no ledger writes). `MainWindow` = the dashboard (tab per listed estate, patch strips, exception-first water column, Watered column = `LastTended` age; its hover carries the exact local time, " - external" when another hand set the clock, and the last-fed line from `ReceiptLog.LastFertilizedAt` (scanned only on the hovered row - never per row per frame); Tend All names the patches it covers AND claims only the filtered bed count, with per-patch skips in the tooltip; the amber "reads empty now - harvested?" overlay waits for `CensusPump.MapAnsweredThisVisit` because objects can settle before the DataMap on a cold zone-in). `RunLogWindow`; `ConfigWindow`.

**`EstatePort` (`Game/EstatePort.cs`) - estate teleports.** THE LAW: `Fire`'s only caller is a button click - never a timer, event, or transition. Cast gate = `ActionManager.GetActionStatus` on action 5 (the game's own refusal reasons). `UpdateAetheryteList` before every read - a session that never opened the teleport window holds an empty list and `Teleport()` on it fails SILENTLY. The call is gated on `Player.Available`: `Telepo.Instance()` SURVIVES the zone-transition player teardown, so it is not a sufficient null gate (an ungated call from the draw loop mid-loading-screen crashes the client - field receipt 2026-08-23). The refresh skip does not consume the throttle, so the first frame back gets a fresh list. Estate join = `TeleportInfo.HouseId` decomposed against the census `EstateKey` with EstateSensor's corroboration idiom (exact district; ward/plot off-by-one tolerance - HouseId's 0/1-based convention is unconfirmed) and the one-survivor-or-no-button rule. The teleport lands at the estate entrance. Button disabled while any chain runs (a teleport would strand it).

**`CensusPump` (`Game/CensusPump.cs`) is the heartbeat**: sensors read, receipts route, the ledger learns. `RefreshDisplayOnly` is the UI-read-without-recording path (post-run settle poll - do not add observations from it). Both the new-estate arrival AND the front-door inside/outside flip retry their map read until the side underfoot answers non-empty when the ledger expects content there - the DataMap populates a beat after any zone line, and a one-shot read that races it stands stale for the whole visit. `ReconcileAbsentPots`: a vanished pot entry = harvest happened unseen - but the verdict needs corroboration, because DataMap-vs-object-table settle order is unreceipted and a wrong verdict Rebase-clears real anchors: settled objects seen, map answered non-empty this visit, a prior settled read exists, and the key absent from BOTH consecutive settled reads (union spares either). Named cost: an estate harvested bare between visits keeps its amber "harvested?" rows rather than auto-clearing. `ActInstant` stamps a chain's plant at its act. `GardenService.AppendOwn` is the ONE seam for an own receipt: it appends to the receipt log AND hands a plant/harvest to the history in the same call; nothing appends to `Receipts` directly.

## Household sync

**The relay serves at balamb.driftlessdigits.com** (repo DriftlessDigits/BalambRelay -> Vercel `balamb-relay` -> Neon; dumb by law - six-field envelope check only, idempotent insert per id, forward-ordered GET with opaque cursor, 21-day retention). **OPEN HOUSEHOLD**: the relay configures NO credential - any well-formed bearer (64 lowercase hex) IS a household, its SHA-256 namespaces the rows, two phrases = two sealed buckets, typing the phrase is the entire setup on every install. Anti-abuse = caps, not secrets: 5,000 rows/household (429, outbox holds, retention drains), 100-distinct-household fuse (paid on first write), `X-Balamb-Client` stamp as a scanner speed bump (401-uniform on stamp/auth failures). The client:

- **HKDF contract**: `HouseholdKeys` constants are THE RELAY'S (salt `BalambGarden.HouseholdSync.v1`, info `auth-token`/`naming-key`); frozen vectors pin both sides (C# test + the relay's derive test, same bytes forever). The phrase lives ONLY in `Configuration.SyncPassphrase` (empty = sync off, zero network surface; password field with an unmask eye). `RelayFingerprint` = SHA-256 over the bearer token string = the household's relay namespace, shown as "Household id" DEBUG-ONLY. Nothing is ever set server-side.
- **HouseId banks at the ACT**: the wire canonical hashes the raw 8 bytes and EstateKey is lossy, so `LoggedReceipt.HouseId` is captured at open/line time (`EstateSensor.CurrentHouseId`: indoor read inside - carries the room - general read outside; both stances field-proven). 0 = honest unknown, refused at send. A v1 receipt log mints a fresh era + Version 2 on first load; pre-houseId entries are history, never cargo.
- **Sender** (`Sync/RelaySender`): framework-tick, self-throttled (60s idle / 5m failure / 15m dam), HTTP off-thread, ack marshaled back (MarkSent + save on the framework thread only). Offline queue IS receipts.json. `WireOutbox` is the ONE place entity pseudonyms mint (pot-vs-bed dispatch lives in `EntityName.For` - byte agreement between mint sites is load-bearing); patch-id-0 / house-id-0 refusals DAM the batch at the entry (a single high-water mark cannot skip honestly); batch cap 500 = the relay's. **`Sync/RelayClient` owns the one HTTP transport** (bearer + `X-Balamb-Client` stamp on both paths); sender and poller keep only cadence + ack.
- **Poller** (`Sync/RelayPoller`): 60s at an estate / 5min idle / zone line pulls next poll to +8s. **`RelayCursor` rides ledger-v2.json** - the cursor is a claim about what THAT FILE absorbed. `RelayFeed.Parse` is all-or-nothing; an unknown future kind word fails the parse and the poller backs off until the install upgrades (a ticket holds the keep-or-skip decision). A quiet page logs nothing; a page that applied, parked, or recorded anything logs one summary line.
- **Foreign replay** (`Engine/Sync/ForeignApply`, pure). **`AbsorbPage` is the whole inbox step and owns the cursor gate**: apply the page to the ledger, record its plants/harvests into the history, SAVE the history, and only on a successful save advance `RelayCursor` (a failed save holds the cursor, the page re-arrives, every apply is idempotent by id; the poller WARNs `cursor held`). Own-user skips by id; matched harvest = the emptying witness (Rebase, HarvestWitnessed); tend/potwater = `ClaimedBed.Tend` under THE RULE (an older tend naming a different known species is refused); plant = `ClaimedBed.Plant` (last edit wins - a sowing is a new planting whoever's hand; older-and-conflicting goes to history only); stage/ripe = `Absorb` (older-and-agreeing tightens the stage bracket, newer-and-contradicting resets then folds); fertilize + potwilt = honest no-ops (the game's refusal line backstops the fed race; wilt derives locally). Enums persist by NAME (`JsonStringEnumConverter`) - the hazard is renaming, not reordering. **Unmatched receipts PARK in `LedgerStore.ForeignHold`** beside the cursor (restore rewinds both together), retried on every fresh mint, pruned at 30d. Two named limits, both by design: the fed-check does not hear foreign fertilizes (foreign entries must never enter ReceiptLog or they re-ship as ours; a ticket holds the ruling); history from an estate this install never censused is a blind spot (no access = no history).
- **Entity ids mint at census time** (`CensusPump.MintWireEntities`): the HMAC inputs exist only standing at the estate. **Stance is part of the identity** - indoor HouseId carries the room, so pots mint INSIDE and beds OUTSIDE, never across the door. Cached on `ClaimedBed.WireEntity`; beds wait on gimmick scan range.
- **Observations mint on CHANGE** at the sighting seam (`SightingChange` out of OnMapSighting): stage climb -> Stage, reaching 4 -> Ripe, source `sighting`; new row / re-read / new planting emit nothing; a climb from stage-0 belief emits (more-data amendment). Honest-skip when houseId or gimmick is missing - the record keeps the sighting either way. PotWilt is not minted: b4's meaning is unreceipted (a ticket holds the capture).
- **Hands and the external display**: hands are opaque wire slugs everywhere (ledger, history, wire, relay, repo). The Watered hover says " - external" when `LastTendedBy` is not own - DERIVED, never stored twice. The ONLY place a slug meets a label is `Configuration.HandAliases`, a local alias seat the player fills (empty = "household"); no screen edits it yet (phase 2). Phrase change = NEW HOUSEHOLD: `LedgerStore.ResetHousehold` clears every household-scoped by-field, parked receipts, and the cursor, and the ConfigWindow clears the alias map with it; timestamps and own receipts stay.

## Receipts

**The receipt lifecycle is two-phase.** A chain's act OPENS a pending receipt; the game's own chat line CLOSES it. One receipt, two witnesses: the chain contributes armed identity, the game contributes the fact it happened. Design canon: the Receipt Lifecycle design in the maintainer's private notes.

- **Open at the ACT, never at delivery.** Every chain calls `CensusPump.OpenAtAct` at its commit moment - the option click, the sow Yes. Opening at delivery double-receipts: the line lands during the map settle, finds no pending, and the manual branch fires a second entry. The one exception is the diff-bind pot path (`_potKey` null): identity is born from the map diff AFTER the act, so it cannot open early and degrades honestly (late open, already delivered, closes chain-unconfirmed).
- **Close** = `CensusPump.TryCloseChain` on a classified line (same verb + container within `ReceiptLifecycle.CloseWindow` 6s) -> history entry, source `chain`. The desk banks a `RecentClose` memo so a delivery arriving AFTER its line already closed (`DeliveryAlreadyClosed`) does not re-open a duplicate; both race orderings are field-proven.
- **Timeout** (`SweepPending`): delivered but no line -> `chain-unconfirmed`, WARN, written (the count is the instrument that would earn a chat-as-primary rethink). Never delivered AND no line -> CANCEL, logged, nothing written (two absent witnesses = no fact).
- **Manual acts = the unclaimed close**: a recognised line with no pending and no chain driving becomes its own receipt via the chat-identity ladder, source `chat`. While `Plugin.AnyChainDriving`, the manual branch is CLOSED (one character, one pair of hands - the line is logged and dropped).

**`ChatReceipts` (`Game/ChatReceipts.cs`) - the closing half. NOT debug-gated; it ships.** Passive listener. Classification is a pure Engine function (`Engine/Sync/ChatLine.cs`): structure first - success = SystemMessage/57 + src=LocalPlayer, refusal = ErrorMessage/60 (never receipted) - then EXACT text match ("You spent 303 gil." rides the same structure; exact-match is load-bearing). Catalogue: bed fertilize / pot fertilize / pot plant / bed tend / pot water (pot "Tend Crop" IS watering), **the bed sow line** ("You plant seeds in the 1st bed, 1st patch." - 57 + src=LocalPlayer; the one garden line that names its own container, as 1-based ordinals, so it is a SHAPE match in `ChatLine.ParseBedSow`, suffix-checked, beds 1-8; it names no seed), plus **the obtain lane**: the harvest close is `LootNotice/62 + src=LocalPlayer` with an ItemPayload - NOT 57 - and cannot exact-match (text varies by count and crop), so `ChatLine.ClassifyObtain` matches structure only and the payload's item, resolved through the species join, is the extra witness. The obtain line names no container (`ChatLine.NamesContainer`), so the pending's own container carries the close; the line's quantity is parsed and banked at close, so `harvest.yields` travels on both own harvest paths and lands in the history; a resolvable item contradicting the pending's species refuses it (times out chain-unconfirmed, honest). Manual harvests demand `HarvestCorroboration`'s MANDATORY two agreeing witnesses (item species + container's last-read species) - the obtain shape is the game's generic loot channel and a from-inventory lockbox needs no target, so absence-proceeds would mint phantom harvests. Named cost: manual FLOWER harvests never receipt (a bouquet resolves to no species); mod flower harvests close via their pending. Refusals at a garden target log at WARN. **The bed sow, both branches**: a chain's plant pending closes only on a sow line naming THAT bed (`ReceiptLifecycle.Matches` `lineBed`); a manual sow needs the line's bed and the previous-target to agree (fail closed, WARN, on disagreement), then `CensusPump.OnSowLine` banks the line's estate, house and instant and lands a Plant receipt once the map names the seed - at once when it already does, else parked and polled every 250ms (display-only reads) for up to 10s; leaving the estate or the timeout lands it species-unknown with a WARN. Planted-at is always the LINE's instant. The map named the seedling within 2.8s of the line in every 2026-10-18 capture. **The hand bed harvest receipts** through the manual obtain branch (field-fired 2026-10-18). **The cross seed rides the harvest row** (`HarvestGather`, ruled 2026-10-18): a crossing harvest prints a seed-bag obtain line in the crop line's millisecond; a miss prints nothing. So a BED harvest's row (both branches - the chain's close and the manual receipt) waits a 2s listening window before it is appended: the census empties the bed at once, only the row waits. `ChatReceipts` asks first whether an obtain line's item is a seed in the crop table (`SeedLineOf`) and offers it to the listening harvest (`CensusPump.OfferSeed`); a seed line with nothing listening WARNs (late or non-garden), except a seed item that is also a crop (garlic), which goes on down the harvest path. Three states on the row and the wire (`seedQty`/`seedItem`): crossed (n, item), missed (0, null), NOT HEARD (null, null) - every row before this, chain timeouts, pots (no cross), and installs that do not report seeds; not-heard never counts as a miss. One window at a time: a new harvest closes the previous one first. A different second seed is refused; the same seed adds. Plugin unload lands the listening harvest (not heard if its window was cut short and nothing came) and every parked sow (`CensusPump.Shutdown`). `NoteUnmatched` (aperture 57-or-62) logs any success-shaped unrecognised line while a pending is open as a candidate close text - it hears lines only during a MOD chain; it is not an ambient capture. Manual identity = PREVIOUS-target at line time, defended fail-closed: kind-vs-object cross-check, plus beds-only species corroboration (`FertilizeCorroboration`, 10s window) against the crop-name inspect line (57 + src=None; FIRST LINE ONLY - the message carries a second payload behind a newline, and the whole TextValue never resolves).

**Identity: wire id = `user:era:counter`.** `user` = stable slug in Configuration (mine-vs-external forever). `era` = volatile slug in the receipt log, names one counter-life; re-minted by `EraGuard` on any of three triggers: counter rewind, fresh log, machine-fingerprint change (covers the clone/migration class a rewind check can't see). `counter` = `ReceiptLog` Seq, monotonic per era. `MachineStamp` = SHA256 of registry MachineGuid, memoized, **LOCAL ONLY - it never travels**; stored hashed in Configuration. Accepted lossy edge: full wipe = new user id, own history replays as external.

**`ReceiptLog` (`receipts.json`, via `GardenService.Receipts`)** - append-only, doubles as the sync outbox (`LastSentSeq` high-water mark; outbox scoped to the current era). Entries carry kind/source/estate/identity/data; entity pseudonyms (HouseholdKeys HMAC) mint at SEND time only - the log itself is local-plaintext. Append-only is law: a duplicate produced by a since-fixed bug stays (nothing sent), it is never edited out.

**Wire types** (`Engine/Sync/SyncReceipt.cs` + `HouseholdKeys.cs`): envelope per the ratified schema; enum words via `WireWordPolicy` - kebab-case default with a CLOSED pin table (`potwater`, `potwilt` stay single words). `chain-unconfirmed` is a source word in the relay's accepted vocabulary. Bed patch id: the PRIMARY source is the acted object's own gimmick, threaded from the chains (`_currentBed`, banked at each gate) through `OpenAtAct`/`OnBedReceipt`; the pump cross-checks its ordinal against the menu header (`ActPatchId`) and falls back to the proximity scan only on disagreement. The send path refuses any entry carrying patch id 0 (fail closed, one guard, no resolution machinery).

**Build stamp**: `StampBuildInfo` csproj target embeds git commit/branch/BuildTime as AssemblyMetadata (BuildTime changes every build, which defeats incremental staleness); `BuildStamp.cs` reads it; shown on the Recon tab and logged at plugin load. "Am I on the current build" is a read, not a guess.

## Storage (plugin config directory)

- `ledger-v2.json` - the LedgerStore (filename kept; file `Version` 4). **Fail closed**: an unreadable ledger is parked as `.unreadable-<stamp>`, never overwritten. **Migrations run once at load, the file first copied to `ledger-v2.json.pre-v<target>.bak`** (never overwritten if present): **v2 -> v3** (`FoldLegacyRings`) folds each row's old observation ring (read through `ClaimedBed.LegacyRing` - the serializer silently drops unmapped properties, so the seam has to exist) into stage brackets + the newest tend; only post-harvest same-species entries fold; unknown hand = null. **v3 -> v4** (`RenameFenceFields`) moves the fence from its old on-disk names onto `PlantingResetAt`/`PlantingResetReason` through a read-only seam (`LegacyFenceAt`/`LegacyFenceReason`); the new name wins if both exist; the one renamed reason member maps by text. `LedgerMigration.NormalizeEstates` runs idempotently after (files from before the estate split held one physical plot as two records).
- `history.json` - `GardenHistory`, append-only, both hands, Plant + Harvest only, dedup by wire id, written on first append (not at load; there is no back-fill from receipts.json). Its own lifetime: a parked ledger never takes the history with it. Never the outbox.
- `trail.jsonl` - append-only receipt + rebase trail (evidence, not memory).
- `receipts.json` - the `ReceiptLog` (own history + sync outbox). Same fail-closed park-on-unreadable rule as the ledger.
- The POC ledger inside `Configuration` is **never read** (a ticket holds remove-or-keep).

`Crops.json` (81 crops: grow/wilt/wither hours, seed joins) · `CrossbreedPairs.json` (3,886 pairs) · `SpeciesIndex.json` (DataMap species u16 -> names) · `Soils.json`. `DomainTables` also carries `TalkAliases` - receipts-only name aliases ("Royal Kukuru Bean" -> "Royal Kukuru"); **reveal-never-invent**: a new alias entry requires a receipted string. ## Failure signatures (field-tested)

- Stale behavior after build -> the x64 flag was missing.
- `PotObject` is a record **struct** - copies mutate silently if you forget.
- UI automation: HousingGardening component nodes are Type >= 1000 (a plain node scan never sees them); buttons take `ButtonClick`, not `MouseClick`; the winning plant path is OpenForItemSlot -> context-menu Use by name -> ClickAddonButton, with settle beat + empty-slot icon baseline `0xFFFFFFFF`.
- Colored Talk names strip to base; an unresolvable Talk name lands receipts as unknown -> check `TalkAliases`.
- Outdoor wilt has **no client-side state anywhere** (DataMap + EventObject + HousingObjectManager all snapshot-diffed across a live watering: zero bytes). Prose at tend time is the only channel. Do not go hunting again without a new lead - the empty search is receipted.
- Last chain step has no successor to trigger a map re-read -> displays race; that's what the post-run settle poll (`RefreshDisplayOnly`) is for.
- Game-state singletons outlive their contents: `Telepo.Instance()` is non-null while the local player is destroyed mid-zone - gate native calls on `Player.Available`, not on the instance pointer.
- One-shot reads of settle-async state (DataMap, object table, teleport list) are race bugs that test clean - every such read needs a retry-until-answered or corroboration pattern, and "worked in the field lap" is not evidence against a race. The DISPLAY is a consumer too: when the recording side learns a settle lesson, ask what the rendering side reads.
- A per-read ring is not history: observing on every read saturates any bounded buffer with same-state sightings and evicts the anchors it was built to keep. Keep bounded first/last brackets, not rings.
- A status word in this file ("owed", "not yet", "in flight") rots silently; nothing fires to retract it. State the mechanism; put the owed work in a ticket.

## Release

The runbook is `Balamb Release` in the maintainer's private notes - run it, don't improvise. The short shape: version lives in `BalambGarden/BalambGarden.csproj` (`<Version>`), user-facing changelog in `BalambGarden/BalambGarden.json` (`Changelog`); bump both on the feature branch, merge --no-ff to main, tag `vN.N.N.N`, push tag. **The tag push triggers `.github/workflows/create_release.yml`** (thin caller into DalamudPluginRepo's reusable workflow): CI builds Release, creates the GitHub release with `latest.zip`, and pushes the version-stamped manifest to the plugin repo, whose pluginmaster regenerates itself (never hand-edit it). Requires the `PAT` secret on this repo. Dev loads read `images/icon.png` beside the DLL; `IconUrl` is fetched only for repo installs; the game caches the icon image across restarts.

## Debug-only instrumentation

`ReconProbe` (debug builds): raw hex dumped verbatim beside every decode so a decoder bug is visible, not hidden. `PlantFlow` watcher is `#if DEBUG`. `ChatRecon` (`Game/ChatRecon.cs`, whole file `#if DEBUG`): passive chat listener for manual-action capture - per line: LogKind, source/target relation kinds, sender, verbatim text, payload shape, and hard/soft/previous target decoded to bed gimmick or pot key. Manual toggle on the Recon tab ("Watch chat"); survives zone lines; never handles or suppresses a message. Capture receipts live under `captures/`: manual-verb success lines are SystemMessage/57 with src=LocalPlayer, refusals are ErrorMessage/60 with src=None (wording varies, structure does not); the acted object rides PREVIOUS-target at line time (hard target is cleared by then).
