# CLAUDE.md - Balamb Garden

Dalamud plugin for FFXIV gardening: census, timers, and one-press tend/harvest/replant chains for the household's estates. Command: `/garden`. This doc is the machine - how the code works, as it stands. It states what IS; the history of how it got here lives in the maintainer's private notes, and owed work lives in tickets, never in this file. Product direction and design rationale live in the maintainer's private notes (the Rebuild Spec is canonical). Reviewed at every merge to main.

## Build laws (read first)

- **Always `-p:Platform=x64`.** An unflagged build produces a stale/mismatched DLL that Dalamud loads anyway.
- **Agents NEVER build the plugin.** Dalamud hot-loads the output DLL - any build is a live deploy into a running game. Builds happen only on the player's explicit "go", never while they may be in-game or testing. Whether Dalamud reloads a rebuilt dev plugin is a per-plugin toggle in the plugin installer ("automatic reloading"); with it off the player reloads by hand, with it on the build IS the reload, which is exactly why no build happens without the player's go.
- **The dev-load DLL is `BalambGarden\bin\x64\Debug\BalambGarden.dll`** - the game loads it in place from the dev plugin location, so a Debug x64 build of the plugin project IS the live deploy. What is live = that file's write time plus the plugin's `build <sha> on <branch>` line in the Dalamud log at load (see Build stamp).
- **Bench draws this plugin's real windows out of the game** (private tooling, not in this repo): it compiles a mirror of this checkout in its own folder, never builds here and never writes to the dev-load folder or the plugin's data; no code or build step here depends on it.
- **The Release build carries only what the player uses.** Anything that exists for our own tooling (Bench, probes, capture listeners) runs, reads and writes only under `#if DEBUG`; a Release install never does it. Check every new file, write or listener against this at review. Pure Engine types a debug feature uses may stay ungated: they do nothing unless called.
- **Tests are safe anytime**: `dotnet test BalambGarden.Engine.Tests/BalambGarden.Engine.Tests.csproj` - the Engine has zero game dependency. A compile check of the plugin project goes to a scratch output folder (`-o <scratch>`), never to the dev-load path.
- Feature branches only; merge to main (no-ff) = save point; this doc's review rides every merge.
- Repo is quasi-public. The maintainer persona is **Drift** (GitHub: DriftlessDigits); no real names in code, comments, commits, or docs; no private paths, and nothing that identifies the maintainer, their machine or their setup. Naming Bench is fine. No AI co-authorship lines in commits. A machine-local pre-commit name guard backs this up (installed per machine from the maintainer's own tooling; untracked BY DESIGN - a tracked hook would ship the names it blocks).

## Architecture: five layers, one-way flow

Each layer knows only the layer below. **Acting IS censusing**: chains emit dialogue receipts that flow back in through the pump.

1. **Sensing** (`Engine/Sensing/` + `BalambGarden/Game/`) - stateless readers.
   - `MapSensor`: housing DataMap decode - outdoor 48-byte entries (8 beds per patch key), indoor per-pot sub-entry 0. Formats in `Engine/Sensing/MapFormat.cs` (bytes 4-5 are allocator junk - never read them). **Indoor zeroed entries are KEPT as unoccupied readings**: a harvest zeroes an entry in place, so a zeroed entry is the map positively saying "empty"; an all-empty room is proof the map answered. Consumers wanting growing pots filter on `Occupied` themselves (Water All and the replant settle poll do).
   - `ObjectSensor` / `GimmickId`: nearby bed objects - GimmickId bytes carry [bed index][patch ordinal][patch-id u16]; reach verdicts at full precision.
   - Pot identity is a **direct read** off the pot object: `HousingFurnitureIndex` + `BaseId` (= HousingFurniture sheet row). `FlowerpotSheet` derives the 3 flowerpot rows by name scan, fails loud on drift.
   - `RosterSensor` / `EstateSensor`: permission from real game data - HouseId direct equality decides "ours"; unfittable rows fail CLOSED and log raw. The roster is read on ARRIVALS, never on a clock: plugin load, login, and every zone line (`Plugin.OnZoneLine` / `OnLogin` -> `RosterSensor.NoteArrival`). Each arrival reads every 2s from the game's first answer for a 10s settle window and keeps the last read (the teleport list is settle-async); between arrivals the roster is held. Reads stay lazy - they happen only when the dashboard or the census pump asks. A refused read (no player yet - normal mid-zone) logs once at DBG and retries; it warns only if still refused 30s after the first refusal. Named cost: an access change while standing still shows at the next zone line. Bench holds a roster it set by pinning `nextRefreshUtc` to forever, so that field's name and meaning are load-bearing.
   - `PotPigment`: indoor byte 2 = (pigment<<4)|stage; only receipted nibbles are interpreted, a color is never guessed. Stage 4 is ripe and **stage 5 is dead** (`GardenStage.Dead`; four dead onion pots read it 2026-11-10, wilt byte 2 - the same 2 ripe flowers read, so the wilt byte is no death signal). Outdoor beds read stage as the whole byte 2; a dead bed's value is unreceipted and read as 5 the same way.
2. **Census** (`Engine/Census/`) - the join and record brain. A row is CREATED by a sighting on a listed (rostered) estate; a bed is BOUND to a map key only by a receipt: `JoinShortlist` proposes patch<->key candidates from diffs, `JoinConfirm` keeps exactly one survivor or nothing. **There is no Claim() method and no pattern-bind path.** Receipted interactions are `ReceiptEvent`: Tend / Harvest / Plant / PotWater. `AccessRoster` scopes the census: not listed = not tracked.
3. **Ledger** (`Engine/Ledger/`) - `LedgerStore` persists the beds + bindings (file `Version` 4). `ClaimedBed` = **one bounded planting record per bed** - a planting is one plant's life in one bed, sow to harvest: `Latest` (newest content read), `PlantedAt`/`PlantedBy`/`PlantedSpecies`, `StageSeen[stage] = first/last seen` (one bracket per stage, min/max fold, replay-idempotent, never evicted), `LastTended`/`LastTendedBy`/`LastTendedSpecies`, a pot's `WiltSeenAt` (the last live read that showed it wilting under `PotWiltRule`, written by the census's pot sighting; cleared by a read showing it not wilting, by a landing watering newer than it - own or relayed - and by any reset whose cut reaches it; own sightings only, the relay's potwilt stays a no-op), a pot's `SeenFineAt` (the last live read that showed it growing - below ripe - and not wilting, written by the same census sighting; the floor under its water clock, a bound and never a receipt; a wilting read leaves it standing, a reset whose cut reaches it clears it; own sightings only), and the fence `PlantingResetAt`/`PlantingResetReason`. **THE RULE**: an older receipt never overwrites newer evidence - if it agrees with the current plant it adds its evidence (`Absorb` -> FoldedOlder), if it contradicts it goes to history only (ledger untouched, counted as replant evidence); only evidence NEWER than everything it contradicts may reset a bed. The fence only moves forward and writes at or before it are no-ops. The fence and the older-test apply to receipts from the other install; this install's own live acts and own live map reads are never measured against it (they are, by definition, the newest thing this install knows). `Rebase(reason, cut)` is the one reconcile path and is **reasoned, logged, time-aware**: every reset names a `RebaseReason` (HarvestWitnessed / ReadsEmpty / NewPlantingSighted / PotAbsent / PlantReceipt), removes only evidence at or before its cut (a sighted replant cuts at the old planting's newest content evidence; a plant receipt cuts at the sowing instant), and returns a `RebaseEvent` the plugin logs (`CensusPump.ReportRebases`: INF when anything was removed or a harvest was witnessed, DBG otherwise) and appends to the trail. **The game wins on content mismatch**, and **a Harvest receipt rebases the record at once** (the receipt is the emptying witness - the row stays, contents and clocks leave); the two-settled-reads reconcile is for UNWITNESSED harvests only. **A sighted replant** is `ClaimedBed.Contradicts`, the one rule the live read and the wire both ask: a different known species, the same species at an earlier stage than its brackets reached, or any stage below 5 after a dead read (`ReadsDead`). A dead plant stays at 5 until cleared and the brackets keep 1-4 only, so the third test is what resets a pot cleared and resown with the same crop; stage 0 counts there, because the read becomes `Latest` either way and would otherwise erase the dead read. `Hand` = own vs an opaque wire slug - the ledger never holds a name. `DebugTrail` (trail.jsonl) is append-only evidence the engine never reads back. `GardenHistory` (`history.json`) = every Plant and Harvest from every hand, forever, with yields and (harvests) the cross seed in three states; `HistoryQuery` is the filtered read side (rows by estate, crop, hand - one hand's slug, or `Own`: this install's hand or every other hand at once - and kind, newest first; the History tab reads it through `GardenBoard.History`, which narrows it further by the hand filter's pick); the yield book (`GardenBoard.Yields`) reads every entry itself.
4. **Derivations** (`Engine/Derivations/`) - pure functions. Every timer is an `EtaWindow` (never a point) with `Provenance` (anchored / bracketed / estimated). `StageModel.RipeWindow` anchors on `PlantedAt` when present, otherwise brackets from the `StageSeen` first/last instants (two or more stages seen = bracketed, one = estimated). The fence is a floor on the sowing (every reset cuts at or before the old contents were last true): when `PlantingResetAt` tightens the earliest end, the window is bracketed - "emptied at X, seen growing at Y" pins a fresh replant to minutes; a fence that would invert the stage bracket is ignored, never a contradiction. `ClockWiltSource`: Watered -> Due -> Overdue -> Danger from the clock's start + crop wilt hours, beds and pots alike (a crop wilts wherever it grows; the flowerpot flowers have no crop row, so no clock reaches them); the recorded start (`RecordedStart`) is the last heard tend, else the witnessed sowing (`PlantedAt`; a plant rebases at its own instant, so a surviving tend is always the later), else none; a pot seen fine floors it (`SeenFineFloor` = `SeenFineAt` minus the crop's wilt hours: not wilting at T proves a watering after T minus them), and the clock starts (`ClockStart(bed, crop)`) at the later of the two, else no clock (Unknown); `RestsOnSeenFineFloor` when the floor is strictly the later (a tie goes to the receipt); `WaterBy` = start + wiltHours (the water deadline), `DiesAt` = start + witherHours, `TendUnheard` = a bed or pot with no watering heard (tend or pot-water); live stage 4 (ripe) forces NotApplicable - fully grown cannot wilt. **`GardenBoard`** (`Derivations/GardenBoard.cs`) is the Garden tab's whole brain: from the ledger estates the roster covers, the beds, the tables and the clock (plus `Standing`: where the player stands, whether inside, and the live indoor read). A pot wears its clock's look like a bed, and where the game speaks the game wins it (`WiltShown` on the cell): in its room the live read alone decides, read only while inside because the last indoor read outlives the room and a house's pots share the yard's estate key - wilting when it shows wilting, and not wilting or dying when it shows the pot fine, whatever the clock says; everywhere else the pot wilts on its record's `WiltSeenAt` while its contents read below ripe; a shown wilt on a clock already dying stays dying. A pot whose clock rests on the floor alone has its deadline at the look itself, so its Overdue draws `WaterSoon` ("may wilt any time"), not `Wilting`, and Danger still draws `Dying` (the earliest it could be dying); the cell carries `SeenFineAt` (the "?" and its hover), except where the game shows the wilt; the card's `DeadlineSeenFine` (the newest look, and whether any has passed its floor's dying point) is set when every bed or pot setting the deadline rests on the floor (the headline then says "water to be safe", or "water now" once they may be dying, beside "seen fine 10m ago", instead of a deadline already behind it), and then the lane's water bar starts at that look (`SeenFine`), never at the floor, so only the drop shows. It returns the visit cards, most urgent first (water deadline; estates with no water clock after, a plant seen ripe first, then by next ripe window): one per estate holding a known planting, each with its deadline (the earliest bed's or pot's) and `FirstToWilt`, the no-watering-recorded count (`TendUnheard`), the water / harvest / replant chips (`ChipSpan`; the water chip counts beds and pots; the replant chip counts the emptied and the dead), the ripe groups (each crop's earliest window, bed crops within `RipeGroupSpan` sharing one, the pots one group of their own, provenance kept), the pot-wilt count (`PotsWilting`: the pots whose wilt the game showed, never one wilting by its clock alone; with `PotsWiltingSeenAt`, the newest sighting, when it comes from the records rather than the live read - the note then says "(seen 12m ago)"), and a picture per patch (eight slots on the game's ring, `RingPosition`) and of the pots, every container carrying its `ContainerLook` (known empty only when a fence says something emptied it; a record never read is `Unread`; the water looks follow the colour map: `WaterSoon` = Due, `Wilting` = Overdue or a pot wilting (live read in its room, else its kept sighting, the cell carrying `WiltSeenAt`), `Dying` = Danger, with `DiesAt` on the cell for the hover; `Dead` = a latest read at stage 5, checked before anything else: no ripe window, no clock, never in ripe-now or the harvest chip, counted in the replant chip with the emptied ones and in the card's `Dead`, with `SeenDeadAt` = that read's time for the "beyond hope" hover), the card's `Thirst` the worst water look among its beds and pots, with `Worst` what wears it. `FirstToWilt`, `Worst`, `Water` and `TendUnheard` are each a `ContainerCount` (beds, pots, and the patch when it is one bed), so the window names the kind and the place, never a number ("A pot wilts at ...", "worst: 4 pots, wilting"); and each card's `TimelineLane` for "the next six days" under the cards: the water bar's start (`WaterFrom` = the recorded clock start of the bed or pot that sets the card's deadline, so the bar is one real clock, or the seen-fine look when the deadline rests on that floor; null with no clock; `FromSowing` when that start is a sowing) and the ripe marks, one per ripe group (anchored = a tick, bracketed = a band its width, estimated = a striped band) plus a "ripe now" mark per row holding something seen ripe (it carries no window), beds row and pots row; each mark is the card's own `RipeGroup` (the lane and the card cannot disagree, ruled at slice 4), every mark starting before the span's end is kept (a window that closed unseen stays, pinned at the left edge: likely ripe and unpicked). `Span(now)` = `SpanBefore` 6h back to `SpanAhead` 6 days, both tunable; `TimelineSpan.Midnights(zone)` gives each day line with that day's own offset (clock changes); `WindowFormat.DayHead` the invariant "Mon 9". The Garden tab draws the lanes under the cards and places what the board returns; the water bar takes the headline's thirst colour (`ThirstColour`); label placement (beside, flipped, or cut at the lane's end) is the window's only judgment. `PotWiltRule`: a pot's map wilt byte claims water only at `wilt==1 && stage<4` (ripe pots broadcast nonzero b4 while the game offers no watering verb at stage 4 - the census's wilt sighting, the estate tabs' two call sites, the garden board and the pot chain's post-water settle consume this one rule; it reads only map bytes, so it lives in `Engine/Sensing/`). `TendSweep`: whether a bed belongs in a tend SWEEP - skip only what the live map CONFIRMED ripe/empty, FAIL OPEN on map silence; single-bed presses are never filtered. **The yield book** (`GardenBoard.Yields`, `Derivations/GardenBoard.Yields.cs`) is the Yields tab's whole brain: from the history, the ledger and the tables, one row per crop, beds and pots apart, rows most planted first. Every sowing in the history is harvested (a harvest of the same crop in the same container pairs with the newest sowing before it; never across containers - a pot whose key moved reads as two), growing (still open, and the ledger record of its container still holds that crop alive: its newest contents name it, not dead) or lost (the rest, a newer sowing in the container ending an older one included), so harvested never tops planted. A harvest with no sowing on record (sown before the history began, or a moved pot) counts in `Unmatched`, never harvested, and its items and cross seed still count (ruled 2026-11-11); a pot's unmatched hover gives no reason, since a pot's key can move. `Gathered` sums yields from the `GatheredFrom` harvests that recorded one; the cross rate is crossed over heard (not heard never counts as a miss), `Firm` from `FirmRateHarvests` (10) heard; the seed shares are per crossing harvest, rounded to add to 100. Pots carry no rate and no shares. **The partner split** (`Derivations/GardenBoard.Partner.cs`): each bed sowing's partner is worked out from its patch at sow when the book is built, never stored: the crossbreed walk (`PartnerAtSow`) looks right, down, up, left from the sown bed on the patch's grid (`RingPosition`) and takes the first bed holding another crop the pairs table can cross with it (`DomainTables.CanCross`); an empty bed, the same crop and a dead plant are skipped, a seedling counts (community knowledge, unreceipted by our captures). No patch on record reads `NotRecorded`, a patch with nothing to cross `NoPartner`; pots never take a partner. A harvest takes its sowing's partner (an unmatched harvest: not recorded). A bed crop whose harvests paired with sowings beside two or more partners carries `Splits`, one row per partner, `NoPartner` after the partners and not recorded last, each with its own counts adding up to the crop's; until then its `Partners` (sowings per recorded partner) ride the crop name's hover. Soil splits nothing (ruled 2026-11-11); the soil a sowing records stays on its history row. `Since` = the history's first entry. **The history page** (`GardenBoard.History`, `Derivations/GardenBoard.History.cs`) is the History tab's whole brain: the rows the filter lets through (`HistoryQuery.Find`, newest first), grouped into the reader's days (`HistoryDay`: a new day wherever the date in the reader's zone changes, a day listed only while it holds a row the filter lets through), each row's estate named (its nickname, else its label; an estate the ledger no longer holds reads its label), the count shown of the whole record and the record's start, and the estate, crop and hand lists the filters offer, from the whole record whatever the filter. The hand list (`HandPick`) is You, each alias on record by name, then Household while a household hand with no alias is on record; a pick shows exactly the rows whose Hand cell reads its word (two hands given one alias share a line), and a pick whose line is gone (its alias changed away) falls back to All hands. The days fold (`GardenBoard.HistoryLines`): a heading per day with its count (`HistoryDayLine`), and the rows only under the days the reader has open; the tab opens on the newest day open (`HistoryOpenOnArrival`), a day landing later arrives folded, and the open days are kept by their midnight across filter changes and landing rows. `HistoryLineIndex` finds a heading by its day or a row by its entry in a new fold, which is how the window holds the line at the top of its view still. The history is its only store. `PotCyclePlanner` builds full plans or refuses (never a half-plan); soil rule: exactly one soil in bags = the soil, else picker. `RunPace`: EWMA (half-old/half-new per completed unit) behind the run-log ETA; pace is TRACKED, never predicted (a pot sweep only learns its verb when the menu opens). Per-chain seeds match dialogue shape; `ChainBase.Eta` is thin wiring over it.
5. **Verbs & UI** (`BalambGarden/Chains/` + `Windows/`) - `ChainBase`: paced dialogue chains (human tempo + jitter, occupied-player guard, clean stop with stated reason; stops land during human-wait steps). `TendChain` (`TendOne` for deliberate single presses; `TendMany` for sweeps - the sweep list is filtered through `TendSweep` before the press, where the count is claimed, and the chain does not re-filter; the list also drops a bed the game will not target, and a patch is in reach only when a bed in it is targetable, because interacting with an untargetable bed opens no dialogue and the sweep stalls on it), `CycleChain` (harvest + replant beds), `PotChain` (pot cycle incl. full-auto plant, `WaterMany` = the pot Tend All - its list is only occupied pots below ripe off the live map (`GardenVerbs.WaterablePots`: neither ripe nor dead); every pot watering ends with its display settle and then one census read, because each receipt sights the room before it lands and a sweep can read a just-watered pot with its flag still up, leaving a wilt sighting newer than the watering), with `PlantFlow`/`PlantFill` doing the read-and-click (no pacing, no ledger writes). **`GardenVerbs` (`Chains/GardenVerbs.cs`, the plugin's `Verbs`) is the one door from a button to a chain**: one method per verb starts the chain and calls `Plugin.Launched`, or starts nothing and returns the refusal sentence for the screen to show; it draws nothing. It also owns what a button offers: the sweep lists (`SweepBeds`, `WaterablePots`), read once for the label and handed back to the press, and the Replant ripe gates (`AnyRipeInPatch`, `AnyRipePotInReach`, from the ledger; the press re-reads the map before it plans). Screens draw and call it; no window starts a chain or reads the bags itself. The bag reads are `Game/BagInventory` (live, no cache: counts, free slots, soils and unknown seeds by the game's item names; the instance is the Engine's `IInventorySource`). `MainWindow` = the dashboard: the **Garden tab first** (`Windows/GardenTab.cs`, draws `GardenBoard.Cards` and nothing else - no rule of its own; every colour value it draws comes from `Windows/Palette.cs`, each named by the one thing it means under the colour map - a new surface picks a meaning there, never a value), then a tab per listed estate (patch strips, exception-first water column, Watered column = `LastTended` age; its hover carries the exact local time, " - external" when another hand set the clock, and the last-fed line from `ReceiptLog.LastFertilizedAt` (scanned only on the hovered row - never per row per frame); Tend All names the patches it covers AND claims only the filtered bed count, with per-patch skips in the tooltip; the amber "reads empty now - harvested?" overlay waits for `CensusPump.MapAnsweredThisVisit` because objects can settle before the DataMap on a cold zone-in). Then the **Yields tab** (`Windows/YieldsTab.cs`, draws `GardenBoard.Yields` and nothing else; every sentence and cell word is `WindowFormat`'s (the column headings are the tab's own), labels and dim values in `Palette.TextDim`; a crop's split rows draw under it, their names dim and indented, and the crop name's hover is `WindowFormat.PartnerHover`; the onion row's name and gathered count draw in `Palette.OnionInk` once it has gathered something (`YieldRow.OnionMark`), the onion mark; over the tables the **trophy line** (`WindowFormat.OnionTrophy` of the book's `Trophy`, an `OnionTally`: onions gathered, onion seeds won by quantity; no line with neither), built with the book, drawn 1.4 times larger in the onion ink between two drawn gold sparkles, with a slow shimmer (`TrophyShimmer`, off ImGui's own clock: a 3 s sweep every 8 s, three clipped copies of the line in `Palette.OnionShine` while the band crosses; nothing on arrival, nothing kept between frames, nothing drawn while the tab is closed); the book is rebuilt once a second or when a history row lands, not every frame). Then the **History tab** (`Windows/HistoryTab.cs`, draws `GardenBoard.History` and nothing else; every sentence and cell word is `WindowFormat`'s (the column headings are the tab's own), labels, day headings, values not heard and "no cross" (a heard harvest that gave no cross seed) in `Palette.TextDim`; an onion harvest's crop and heard yield in `Palette.OnionInk` (the onion mark: `GardenBoard.IsGoalCropHarvest`, Thavnairian Onion only, any hand, bed or pot; the goal crop is `GardenBoard.GoalCrop`; the Yields row reads `YieldRow.OnionMark`, never a split row); the page is rebuilt only when a row lands, a filter changes, or an estate or a hand is renamed, its column widths measured then over every row of the page, open or folded, so opening a day moves no column; each day heading is a tree node in the dim ink with its count (`WindowFormat.HistoryDay`), opened or folded by a click (its id is the day alone, so a count changing mid-click keeps the click), the open days kept until another tab is picked (a window closed, collapsed or hidden keeps them) and the newest alone open each time the tab is picked; when the lines change the window finds the line that was at the top of its view (`HistoryLineIndex`) and moves the scroll by as many rows, set before the table's own window begins (`ImGuiP.SetNextWindowScroll`) so it lands in the same frame, and a landing row, a new day or a day folded above moves nothing on screen; at the very bottom of the list the window's scroll is still held to last frame's height, so there the rest of the move lands one frame later (every row, headings included, is the font's height plus the cell padding: the list clipper and this hold both rely on it); only the rows in view are drawn - the history grows forever). The two tabs share `Windows/WindowText.cs` for a cross seed's name and text at full brightness, dim, or in the onion ink. `RunLogWindow`; `ConfigWindow` (the settings: a fixed 400 wide, at least 500 tall and growing to fit its content, measured each frame, since it has no scrollbar; its Household hands section lists `GardenBoard.ForeignHands` with an alias box each, words `WindowFormat`'s, rebuilt on a new history row or once a second).

**`EstatePort` (`Game/EstatePort.cs`) - estate teleports.** THE LAW: `Fire`'s only caller is a button click - never a timer, event, or transition. Cast gate = `ActionManager.GetActionStatus` on action 5 (the game's own refusal reasons). `UpdateAetheryteList` before every read - a session that never opened the teleport window holds an empty list and `Teleport()` on it fails SILENTLY. The call is gated on `Player.Available`: `Telepo.Instance()` SURVIVES the zone-transition player teardown, so it is not a sufficient null gate (an ungated call from the draw loop mid-loading-screen crashes the client - field receipt 2026-08-23). The refresh skip does not consume the throttle, so the first frame back gets a fresh list. Estate join = `TeleportInfo.HouseId` decomposed against the census `EstateKey` with EstateSensor's corroboration idiom (exact district; ward/plot off-by-one tolerance - HouseId's 0/1-based convention is unconfirmed) and the one-survivor-or-no-button rule. The teleport lands at the estate entrance. Button disabled while any chain runs (a teleport would strand it).

**`CensusPump` (`Game/CensusPump.cs`) is the heartbeat**: sensors read, receipts route, the ledger learns. **The census reads the map only at an arrival, at a front-door flip, just before each receipt lands (`SightNow`), and once after a pot water settle - never on a timer while the player stands still** (the display's settle polls use `RefreshDisplayOnly`, which records nothing). So anything the ledger keeps from a map read (contents, stage brackets, a pot's wilt sighting) is as of the last of those, and in a sweep each receipt's read can see the previous act's lag. `RefreshDisplayOnly` is the UI-read-without-recording path (post-run settle poll - do not add observations from it). Both the new-estate arrival AND the front-door inside/outside flip retry their map read until the side underfoot answers non-empty when the ledger expects content there - the DataMap populates a beat after any zone line, and a one-shot read that races it stands stale for the whole visit. `ReconcileAbsentPots`: a vanished pot entry = harvest happened unseen - but the verdict needs corroboration, because DataMap-vs-object-table settle order is unreceipted and a wrong verdict Rebase-clears real anchors: settled objects seen, map answered non-empty this visit, a prior settled read exists, and the key absent from BOTH consecutive settled reads (union spares either). Named cost: an estate harvested bare between visits keeps its amber "harvested?" rows rather than auto-clearing. `ActInstant` stamps a chain's plant at its act. `GardenService.AppendOwn` is the ONE seam for an own receipt: it appends to the receipt log AND hands a plant/harvest to the history in the same call; nothing appends to `Receipts` directly.

## Household sync

**The relay serves at balamb.driftlessdigits.com** (repo DriftlessDigits/BalambRelay -> Vercel `balamb-relay` -> Neon; dumb by law - six-field envelope check only, idempotent insert per id, forward-ordered GET with opaque cursor, 21-day retention). **OPEN HOUSEHOLD**: the relay configures NO credential - any well-formed bearer (64 lowercase hex) IS a household, its SHA-256 namespaces the rows, two phrases = two sealed buckets, typing the phrase is the entire setup on every install. Anti-abuse = caps, not secrets: 5,000 rows/household (429, outbox holds, retention drains), 100-distinct-household fuse (paid on first write), `X-Balamb-Client` stamp as a scanner speed bump (401-uniform on stamp/auth failures). The client:

- **HKDF contract**: `HouseholdKeys` constants are THE RELAY'S (salt `BalambGarden.HouseholdSync.v1`, info `auth-token`/`naming-key`); frozen vectors pin both sides (C# test + the relay's derive test, same bytes forever). The phrase lives ONLY in `Configuration.SyncPassphrase` (empty = sync off, zero network surface; password field with an unmask eye). `RelayFingerprint` = SHA-256 over the bearer token string = the household's relay namespace, shown as "Household id" DEBUG-ONLY. Nothing is ever set server-side.
- **HouseId banks at the ACT**: the wire canonical hashes the raw 8 bytes and EstateKey is lossy, so `LoggedReceipt.HouseId` is captured at open/line time (`EstateSensor.CurrentHouseId`: indoor read inside - carries the room - general read outside; both stances field-proven). 0 = honest unknown, refused at send. A v1 receipt log mints a fresh era + Version 2 on first load; pre-houseId entries are history, never cargo.
- **Sender** (`Sync/RelaySender`): framework-tick, self-throttled (60s idle / 5m failure / 15m dam), HTTP off-thread, ack marshaled back (MarkSent + save on the framework thread only). Offline queue IS receipts.json. `WireOutbox` is the ONE place entity pseudonyms mint (pot-vs-bed dispatch lives in `EntityName.For` - byte agreement between mint sites is load-bearing); patch-id-0 / house-id-0 refusals DAM the batch at the entry (a single high-water mark cannot skip honestly); batch cap 500 = the relay's. **`Sync/RelayClient` owns the one HTTP transport** (bearer + `X-Balamb-Client` stamp on both paths); sender and poller keep only cadence + ack.
- **Poller** (`Sync/RelayPoller`): 60s at an estate / 5min idle / zone line pulls next poll to +8s. **`RelayCursor` rides ledger-v2.json** - the cursor is a claim about what THAT FILE absorbed. `RelayFeed.Parse` is all-or-nothing; an unknown future kind word fails the parse and the poller backs off until the install upgrades (a ticket holds the keep-or-skip decision). A quiet page logs nothing; a page that applied, parked, or recorded anything logs one summary line.
- **Foreign replay** (`Engine/Sync/ForeignApply`, pure). **`AbsorbPage` is the whole inbox step and owns the cursor gate**: apply the page to the ledger, record its plants/harvests into the history, SAVE the history, and only on a successful save advance `RelayCursor` (a failed save holds the cursor, the page re-arrives, every apply is idempotent by id; the poller WARNs `cursor held`). Own-user skips by id; matched harvest = the emptying witness (Rebase, HarvestWitnessed); tend/potwater = `ClaimedBed.Tend` under THE RULE (an older tend naming a different known species is refused); plant = `ClaimedBed.Plant` (last edit wins - a sowing is a new planting whoever's hand; older-and-conflicting goes to history only); stage/ripe = `Absorb` (older-and-agreeing tightens the stage bracket, newer-and-contradicting resets then folds); fertilize + potwilt = honest no-ops (the game's refusal line backstops the fed race; wilt derives locally). Enums persist by NAME (`JsonStringEnumConverter`) - the hazard is renaming, not reordering. **Unmatched receipts PARK in `LedgerStore.ForeignHold`** beside the cursor (restore rewinds both together), retried on every fresh mint, pruned at 30d. Two named limits, both by design: the fed-check does not hear foreign fertilizes (foreign entries must never enter ReceiptLog or they re-ship as ours; a ticket holds the ruling); history from an estate this install never censused is a blind spot (no access = no history).
- **Entity ids mint at census time** (`CensusPump.MintWireEntities`): the HMAC inputs exist only standing at the estate. **Stance is part of the identity** - indoor HouseId carries the room, so pots mint INSIDE and beds OUTSIDE, never across the door. Cached on `ClaimedBed.WireEntity`; beds wait on gimmick scan range.
- **Observations mint on CHANGE** at the sighting seam (`SightingChange` out of OnMapSighting): stage climb -> Stage, reaching 4 -> Ripe, source `sighting`; new row / re-read / new planting emit nothing; a climb from stage-0 belief emits (more-data amendment). Honest-skip when houseId or gimmick is missing - the record keeps the sighting either way. PotWilt is not minted: b4's meaning is unreceipted (a ticket holds the capture).
- **Hands and the external display**: hands are opaque wire slugs everywhere (ledger, history, wire, relay, repo). The Watered hover says " - external" when `LastTendedBy` is not own - DERIVED, never stored twice. The ONLY place a slug meets a label is `Configuration.HandAliases`, a local alias seat the player fills in the settings window (empty = "household"; every slug in the ledger or the history but the own one is offered; `Aliases.Set` is the one write rule: trimmed, a blank box removes the alias, the own tag takes none). `Aliases.Of` is the one read rule (none for the own hand or a blank entry), and `WindowFormat.HandName` the one display: "you", the alias, else "household"; the History tab's Hand cells and hand filter read it. The Garden hovers name no hand (ruled 2026-11-11: who watered does not matter). Phrase change = NEW HOUSEHOLD: `LedgerStore.ResetHousehold` clears every household-scoped by-field, parked receipts, and the cursor, and the ConfigWindow clears the alias map with it; timestamps and own receipts stay.

## Receipts

**The receipt lifecycle is two-phase.** A chain's act OPENS a pending receipt; the game's own chat line CLOSES it. One receipt, two witnesses: the chain contributes armed identity, the game contributes the fact it happened. Design canon: the Receipt Lifecycle design in the maintainer's private notes.

- **Open at the ACT, never at delivery.** Every chain calls `CensusPump.OpenAtAct` at its commit moment - the option click, the sow Yes. Opening at delivery double-receipts: the line lands during the map settle, finds no pending, and the manual branch fires a second entry. The one exception is the diff-bind pot path (`_potKey` null): identity is born from the map diff AFTER the act, so it cannot open early and degrades honestly (late open, already delivered, closes chain-unconfirmed).
- **Close** = `CensusPump.TryCloseChain` on a classified line (same verb + container within `ReceiptLifecycle.CloseWindow` 6s) -> history entry, source `chain`. The desk banks a `RecentClose` memo so a delivery arriving AFTER its line already closed (`DeliveryAlreadyClosed`) does not re-open a duplicate; both race orderings are field-proven.
- **Timeout** (`SweepPending`): delivered but no line -> `chain-unconfirmed`, WARN, written (the count is the instrument that would earn a chat-as-primary rethink). Never delivered AND no line -> CANCEL, logged, nothing written (two absent witnesses = no fact).
- **Manual acts = the unclaimed close**: a recognised line with no pending and no chain driving becomes its own receipt via the chat-identity ladder, source `chat`. While `Plugin.AnyChainDriving`, the manual branch is CLOSED (one character, one pair of hands - the line is logged and dropped).

**`ChatReceipts` (`Game/ChatReceipts.cs`) - the closing half. NOT debug-gated; it ships.** Passive listener. Classification is a pure Engine function (`Engine/Sync/ChatLine.cs`): structure first - success = SystemMessage/57 + src=LocalPlayer, refusal = ErrorMessage/60 (never receipted) - then EXACT text match ("You spent 303 gil." rides the same structure; exact-match is load-bearing). Catalogue: bed fertilize / pot fertilize / pot plant / bed tend / pot water (pot "Tend Crop" IS watering), **the bed sow line** ("You plant seeds in the 1st bed, 1st patch." - 57 + src=LocalPlayer; the one garden line that names its own container, as 1-based ordinals, so it is a SHAPE match in `ChatLine.ParseBedSow`, suffix-checked, beds 1-8; it names no seed), plus **the obtain lane**: the harvest close is `LootNotice/62 + src=LocalPlayer` with an ItemPayload - NOT 57 - and cannot exact-match (text varies by count and crop), so `ChatLine.ClassifyObtain` matches structure only and the payload's item, resolved through the species join, is the extra witness. The obtain line names no container (`ChatLine.NamesContainer`), so the pending's own container carries the close; the line's quantity is parsed and banked at close, so `harvest.yields` travels on both own harvest paths and lands in the history; a resolvable item contradicting the pending's species refuses it (times out chain-unconfirmed, honest). Manual harvests demand `HarvestCorroboration`'s MANDATORY two agreeing witnesses (item species + container's last-read species) - the obtain shape is the game's generic loot channel and a from-inventory lockbox needs no target, so absence-proceeds would mint phantom harvests. Named cost: manual FLOWER harvests never receipt (a bouquet resolves to no species); mod flower harvests close via their pending. Refusals at a garden target log at WARN. **The bed sow, both branches**: a chain's plant pending closes only on a sow line naming THAT bed (`ReceiptLifecycle.Matches` `lineBed`); a manual sow needs the line's bed and the previous-target to agree (fail closed, WARN, on disagreement), then `CensusPump.OnSowLine` banks the line's estate, house and instant and lands a Plant receipt once the map names the seed - at once when it already does, else parked and polled every 250ms (display-only reads) for up to 10s; leaving the estate or the timeout lands it species-unknown with a WARN. Planted-at is always the LINE's instant. The map named the seedling within 2.8s of the line in every 2026-10-18 capture. **The hand bed harvest receipts** through the manual obtain branch (field-fired 2026-10-18). **The cross seed rides the harvest row** (`HarvestGather`, ruled 2026-10-18): a crossing harvest prints a seed-bag obtain line in the crop line's millisecond; a miss prints nothing. So a BED harvest's row (both branches - the chain's close and the manual receipt) waits a 2s listening window before it is appended: the census empties the bed at once, only the row waits. `ChatReceipts` asks first whether an obtain line's item is a seed in the crop table (`SeedLineOf`) and offers it to the listening harvest (`CensusPump.OfferSeed`); a seed line with nothing listening WARNs (late or non-garden), except a seed item that is also a crop (garlic), which goes on down the harvest path. Three states on the row and the wire (`seedQty`/`seedItem`): crossed (n, item), missed (0, null), NOT HEARD (null, null) - every row before this, chain timeouts, pots (no cross), and installs that do not report seeds; not-heard never counts as a miss. One window at a time: a new harvest closes the previous one first. A different second seed is refused; the same seed adds. Plugin unload lands the listening harvest (not heard if its window was cut short and nothing came) and every parked sow (`CensusPump.Shutdown`). **The sow capture rides the plant row** (v0.4.1, Sow Capture design): every bed sow banks its **patch at sow** (`Engine/Sync/PatchAtSow`, pure: the eight `BedReading`s copied RAW by slot - occupied, species, stage - never interpreted, no adjacency; absent when no read covered the patch) and every sow, beds and pots, banks its **soil** (item id). Chain sows: the soil is the one the chain just checked against the sow question (`CycleChain`/`PotChain.ConfirmSow` -> `OpenAtAct(..., soil)`; a pot plan's soil may be 0, so pots take the question's own soil), the act banks the LAST read's patch on the pending and the delivery's fresh read replaces it (`MarkDelivered`); the pot diff-bind route carries the soil into its late open. Hand sows: **`Game/SowQuestion` is a passive SelectYesno listener in the shipping build** (PostSetup reads the prompt through `PlantFlow.ReadStringValue` + `SowPrompt.Parse`, PreFinalize marks it closed; it never answers, and stands aside while a chain drives) that offers the question's soil to the **soil note** (`Engine/Sync/SoilNote`, pure: holds while the question is open - capped at `OpenLimit` = 10 min in case the close is never heard - and `AfterClose` = 6s after it closes (the 2026-11-07 field-fire measured the close-to-line gap at 0.16s for a bed and 0.21s for a pot), a take clears it, a new question replaces it, an unnamed soil clears it); the bed sow takes it AT THE LINE and carries it on the `ParkedSow`, a pot sow takes it at its line; a hand sow with no soil heard WARNs. Soil names resolve through the topsoil table, then the Item sheet by name (`PlantFlow.SoilItemId`; "Potting Soil" is in no table). `ReceiptLifecycle.DataOf` (Engine) turns a pending into its wire data whichever way it closes. The sow-lag race (an empty read just after a sow resetting the fresh anchor) is closed by construction for hand sows (they land only once the map names the seed) and by field evidence for chain sows (no reads-empty reset after any of the 10-18 evening's 45 bed sows, nor the 2026-11-07 field-fire's 23); a reads-empty reset logged right after a sow reopens it. The same lag shows on the dashboard: the chain's post-Yes read lands before the seed, so `CensusPump` holds each chain-sown bed in a `SowSettle` (`Engine/Sensing/SowSettle.cs`, display only, 10s limit) and re-reads on the parked-sow quarter-second poll until the map shows it; while it waits the row does not ask "replanted without me?" (field-fire 2026-11-07: the map showed each chain sow 0.52-0.78s after the Yes, logged per bed at DBG). The chain row's patch-at-sow still lists its own bed empty - the same early read; neighbors are what it is for. `NoteUnmatched` (aperture 57-or-62) logs any success-shaped unrecognised line while a pending is open as a candidate close text - it hears lines only during a MOD chain; it is not an ambient capture. Manual identity = PREVIOUS-target at line time, defended fail-closed: kind-vs-object cross-check, plus beds-only species corroboration (`FertilizeCorroboration`, 10s window) against the crop-name inspect line (57 + src=None; FIRST LINE ONLY - the message carries a second payload behind a newline, and the whole TextValue never resolves).

**Identity: wire id = `user:era:counter`.** `user` = stable slug in Configuration (mine-vs-external forever). `era` = volatile slug in the receipt log, names one counter-life; re-minted by `EraGuard` on any of three triggers: counter rewind, fresh log, machine-fingerprint change (covers the clone/migration class a rewind check can't see). `counter` = `ReceiptLog` Seq, monotonic per era. `MachineStamp` = SHA256 of registry MachineGuid, memoized, **LOCAL ONLY - it never travels**; stored hashed in Configuration. Accepted lossy edge: full wipe = new user id, own history replays as external.

**`ReceiptLog` (`receipts.json`, via `GardenService.Receipts`)** - append-only, doubles as the sync outbox (`LastSentSeq` high-water mark; outbox scoped to the current era). Entries carry kind/source/estate/identity/data; entity pseudonyms (HouseholdKeys HMAC) mint at SEND time only - the log itself is local-plaintext. Append-only is law: a duplicate produced by a since-fixed bug stays (nothing sent), it is never edited out.

**Wire types** (`Engine/Sync/SyncReceipt.cs` + `HouseholdKeys.cs`): envelope per the ratified schema; enum words via `WireWordPolicy` - kebab-case default with a CLOSED pin table (`potwater`, `potwilt` stay single words). `chain-unconfirmed` is a source word in the relay's accepted vocabulary. `SyncData` is flat and ADDITIVE - a new field rides a known kind and older installs skip it (System.Text.Json's default), while a new KIND fails their feed parse: the harvest's `seedQty`/`seedItem` (v0.4.0) and the plant's `soil` + `patch` (`SyncPatchBed[]`: slot, occupied, species, stage; v0.4.1) all shipped this way, and `GardenHistory`'s TWO builders (`FromOwn`, `FromForeign`) must both copy any new field or the household half silently drops it. Bed patch id: the PRIMARY source is the acted object's own gimmick, threaded from the chains (`_currentBed`, banked at each gate) through `OpenAtAct`/`OnBedReceipt`; the pump cross-checks its ordinal against the menu header (`ActPatchId`) and falls back to the proximity scan only on disagreement. The send path refuses any entry carrying patch id 0 (fail closed, one guard, no resolution machinery).

**Build stamp**: `StampBuildInfo` csproj target embeds git commit/branch/BuildTime as AssemblyMetadata (BuildTime changes every build, which defeats incremental staleness); `BuildStamp.cs` reads it; shown on the Recon tab and logged at plugin load. "Am I on the current build" is a read, not a guess.

## Storage (plugin config directory)

- `ledger-v2.json` - the LedgerStore (filename kept; file `Version` 4). A new optional field needs no version bump: nulls are omitted on write and unknown fields are skipped on read, so an older file loads it as absent and writes back the same bytes (`WiltSeenAt` and `SeenFineAt` joined this way; `LedgerTests` pins each with bytes the previous build wrote). **The file's reference bytes** (`Engine.Tests/Ledger/ledger-reference.json`, `LedgerReferenceTests`): an example ledger filling every part of the file must save as exactly that file, and the file must load and save back unchanged, so the bytes any earlier build wrote are `git show <commit>:` that path. A new optional field never joins the example: the test staying green is the proof an older file survives it (the field gets its own round-trip test). An on-purpose format change (a version bump, a rename) fails the test, which writes what it got to `ledger-reference.received.json` beside it (gitignored); the copy over the reference is the format change's diff. A field on `ClaimedBed` must also be copied in `LedgerMigration.Rekey`/`Combine`/`TrimAt` - `NormalizeEstates` runs at every load. **Fail closed**: an unreadable ledger is parked as `.unreadable-<stamp>`, never overwritten. **Migrations run once at load, the file first copied to `ledger-v2.json.pre-v<target>.bak`** (never overwritten if present): **v2 -> v3** (`FoldLegacyRings`) folds each row's old observation ring (read through `ClaimedBed.LegacyRing` - the serializer silently drops unmapped properties, so the seam has to exist) into stage brackets + the newest tend; only post-harvest same-species entries fold; unknown hand = null. **v3 -> v4** (`RenameFenceFields`) moves the fence from its old on-disk names onto `PlantingResetAt`/`PlantingResetReason` through a read-only seam (`LegacyFenceAt`/`LegacyFenceReason`); the new name wins if both exist; the one renamed reason member maps by text. `LedgerMigration.NormalizeEstates` runs idempotently after (files from before the estate split held one physical plot as two records).
- `history.json` - `GardenHistory`, append-only, both hands, Plant + Harvest only (harvests carry yields and the cross seed; plants carry soil and, on beds, the patch at sow - every optional field absent = not heard, which is how older rows load), dedup by wire id, written on first append (not at load; there is no back-fill from receipts.json). Its own lifetime: a parked ledger never takes the history with it. Never the outbox.
- `access-roster.json` - **debug builds only** (it serves Bench, not the player; a Release install never reads or writes it, and the copy from the last dev session stays on disk). `SavedAccessRoster`: the access roster as last read in game (each estate's key and kind, in the order read) and when that read happened. One writer: each `CensusPump` tick hands `RosterSensor.LastRead` (the sensor's cached list and when the game answered it; the sensor itself never writes) to `GardenService.SaveAccessRoster`, which writes only when the list differs from the saved one (an estate added or dropped, or a new order), so the stamp is when it last changed, not when it was last seen. An empty read is never saved (the teleport list settles a beat late). Never read back in game; it exists for readers outside the game (Bench answers the tab set from it). A copy of the game's own answer, so an unreadable file (or one with no read time) is not parked: it loads as absent and the next access-roster read overwrites it.
- `trail.jsonl` - append-only receipt + rebase trail (evidence, not memory).
- `receipts.json` - the `ReceiptLog` (own history + sync outbox). Same fail-closed park-on-unreadable rule as the ledger.
- The POC ledger inside `Configuration` is **never read** (a ticket holds remove-or-keep).

## Failure signatures (field-tested)

- Stale behavior after build -> the x64 flag was missing.
- `PotObject` is a record **struct** - copies mutate silently if you forget.
- UI automation: HousingGardening component nodes are Type >= 1000 (a plain node scan never sees them); buttons take `ButtonClick`, not `MouseClick`; the winning plant path is OpenForItemSlot -> context-menu Use by name -> ClickAddonButton, with settle beat + empty-slot icon baseline `0xFFFFFFFF`.
- Colored Talk names strip to base; an unresolvable Talk name lands receipts as unknown -> check `TalkAliases`.
- Outdoor wilt has **no client-side state anywhere** (DataMap + EventObject + HousingObjectManager all snapshot-diffed across a live watering: zero bytes). Prose at tend time is the only channel. Do not go hunting again without a new lead - the empty search is receipted.
- Last chain step has no successor to trigger a map re-read -> displays race; that's what the post-run settle poll (`RefreshDisplayOnly`) is for.
- Game-state singletons outlive their contents: `Telepo.Instance()` is non-null while the local player is destroyed mid-zone - gate native calls on `Player.Available`, not on the instance pointer.
- One-shot reads of settle-async state (DataMap, object table, teleport list) are race bugs that test clean - every such read needs a retry-until-answered or corroboration pattern, and "worked in the field lap" is not evidence against a race. The DISPLAY is a consumer too: when the recording side learns a settle lesson, ask what the rendering side reads.
- A per-read ring is not history: observing on every read saturates any bounded buffer with same-state sightings and evicts the anchors it was built to keep. Keep bounded first/last brackets, not rings.
- A status word in this file ("owed", "not yet", "in flight") rots silently; nothing fires to retract it. State the mechanism; put the owed work in a ticket.

## Release

The runbook is `Balamb Release` in the maintainer's private notes - run it, don't improvise. The short shape: version lives in `BalambGarden/BalambGarden.csproj` (`<Version>`), user-facing changelog in `BalambGarden/BalambGarden.json` (`Changelog`); bump both on the feature branch, merge --no-ff to main, tag `vN.N.N.N`, push tag. **The tag push triggers `.github/workflows/create_release.yml`** (thin caller into DalamudPluginRepo's reusable workflow): CI builds Release, creates the GitHub release with `latest.zip`, and pushes the version-stamped manifest to the plugin repo, whose pluginmaster regenerates itself (never hand-edit it). Requires the `PAT` secret on this repo. Dev loads read `images/icon.png` beside the DLL; `IconUrl` is fetched only for repo installs; the game caches the icon image across restarts.
